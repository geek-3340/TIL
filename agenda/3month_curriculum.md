# 入社までの3ヶ月 学習カリキュラム

**前提**: 1日2〜3時間 / 週5〜6日 → 週あたり約15時間、12週間で**約180時間**

---

## 0. この3ヶ月の一本の軸

上長のリクエストを1行にすると「**AIに答えを聞かなくても、自分で原因を特定して直せる人になれ**」です。
知識量よりも、**調べ方と切り分けの手順**が身についているかが問われています。

そのために全期間を通して守ってほしいのが次の3つです。

### ルール1: AI禁止タイム（1日のうち最低90分）

学習時間の大半はAIを閉じます。詰まったときの参照順は固定してください。

1. **エラーメッセージを最後まで読む**（スタックトレースの1行目ではなく、自分のコードが出てくる行を探す）
2. **ログを見る**（`storage/logs/laravel.log`、`/var/log/nginx/error.log` など）
3. **公式ドキュメント / `man` コマンド**
4. エラーメッセージ全文で検索（英語のまま検索する）
5. **30分たっても分からなければAI** — ただし「直して」ではなく「自分はAが原因だと考えたがBという結果になった、なぜか」と聞く

> AIは「答えをもらう相手」ではなく「答え合わせの相手」に役割を変える、というのがこの3ヶ月の最大のトレーニングです。

### ルール2: 毎日の型（例: 2.5時間の場合）

| 時間 | 内容 |
|---|---|
| 15分 | 前日の学習ログを読み返す（復習） |
| 100分 | 手を動かす（写経ではなく、自分で壊して直す） |
| 20分 | **学習ログを書く**（後述） |

### ルール3: 学習ログをGitHubに残す

`study-log` リポジトリを作り、日付ごとにMarkdownで残します。テンプレートはこれだけでOK。

```markdown
## 2026-08-08
### やったこと
### 詰まったこと / エラー全文
### 原因はなんだったか（自分の言葉で）
### どうやって切り分けたか
### 明日やること
```

これは3つの効果があります。

- **エラー対応の引き出しが貯まる**（現場で「前に見たやつだ」が発動する）
- **毎日Gitを触るのでGitの練習になる**（後述のコンフリクト練習もここでやる）
- **面談・入社後の1on1でそのまま成果報告に使える**

# Phase 1: PHPを"読める・追える"状態にする（Week 1〜4）

## Week 1: Git補強 + PHP構文①

### Day 1〜2: Git（コンフリクト解消）

上長から「コンフリクト解消ができるように」と言われているので、ここは**わざと起こして潰す**のが最短です。

練習用リポジトリを作り、以下を各3回ずつ実行してください。

1. **同じ行を両ブランチで編集 → merge → コンフリクト**
   - `<<<<<<< HEAD` / `=======` / `>>>>>>> branch` の3つのマーカーが何を指しているか説明できるようにする
   - 手で編集して解消 → `git add` → `git commit`
2. **`git merge --abort` でやり直す**（失敗しても戻れると知るのが精神安定上とても重要）
3. **`git rebase` 中のコンフリクト解消** → `git rebase --continue` / `--abort`
4. **ファイル削除 vs 編集** のコンフリクト（`deleted by us` 系）を体験する

あわせて覚えるコマンド:

| コマンド | 用途 |
|---|---|
| `git log --oneline --graph --all` | 今どういう分岐状態か目で見る |
| `git diff` / `git diff --staged` | 何を変更したか確認 |
| `git stash` / `git stash pop` | 作業中に別ブランチへ行きたいとき |
| `git reset --soft/--mixed/--hard` | 3つの違いを説明できるように |
| `git revert` | 公開済みコミットの取り消し |
| `git reflog` | **やらかしたときの命綱**。必ず一度使っておく |

> ✅ 到達確認: 「resetとrevertの使い分け」「mergeとrebaseの違い」を人に口頭で説明できる

### Day 3〜7: PHP構文の穴埋め

Laravelから入ると素のPHPが穴だらけになりがちです。ここを埋めます。

- **型**: `int/float/string/bool/array/null`、`===` と `==` の違い、型ジャグリング、`declare(strict_types=1)`
- **型宣言**: 引数の型・戻り値の型・nullable（`?string`）・union型（`int|string`）
- **配列**: 添字配列と連想配列、`array_map` / `array_filter` / `array_reduce` / `usort` / `array_column` / `in_array` / `array_key_exists`
- **文字列**: `sprintf`、ヒアドキュメント、`mb_` 系関数がなぜ必要か
- **制御構文**: `foreach` の参照渡し（`&$value`）の落とし穴、`match` 式、null合体演算子 `??` / `?->`
- **関数**: デフォルト引数、可変長引数（`...$args`）、クロージャと `use`、アロー関数

**やり方**: 読むだけにせず、1つのファイルに全部書いて `php -a`（対話モード）や `php test.php` で出力を確認する。
特に「思ってた出力と違った」ものは全部学習ログに残す。

**教材候補**: PHPマニュアル（日本語版・言語リファレンス）／『独習PHP』

> ✅ 到達確認: `array_map` と `array_filter` を使って、連想配列から条件に合う要素を抽出・整形する処理をノーヒントで書ける

## Week 2: PHPのオブジェクト指向と周辺

- **クラス**: プロパティ・メソッド・コンストラクタ、`public/protected/private`、`static`、定数
- **継承とインターフェース**: `extends` と `implements` の違い、抽象クラス、`trait`
- **名前空間とオートロード**: `namespace` / `use` / PSR-4、Composerの `autoload` が何をしているか
- **Composer**: `composer.json` と `composer.lock` の違い、`require` と `require-dev`、`vendor/` の中身を実際に覗く
- **PSR-12（コーディング規約）** をざっと読む

### なぜここをやるのか

Laravelのエラーで `vendor/` の中のファイルがスタックトレースに出てきたとき、**中を読みに行けるかどうか**でエラー解決速度が決定的に変わります。この週の目的は「フレームワークの中身を読む勇気を持つこと」です。

**実践課題**: 自作アプリの機能をひとつ選び、コントローラに書いてある処理をServiceクラスに切り出す。インターフェースを切って、コンストラクタインジェクションで注入する。

> ✅ 到達確認: Laravelのコントローラで型を書いただけでインスタンスが渡ってくる仕組み（DIコンテナ）を、ざっくり説明できる

## Week 3: エラー・例外・ログ

**この週が今回のカリキュラムの心臓部です。** 時間が足りなければ他を削ってでもここは厚くやってください。

### Day 1〜2: PHPのエラーを理解する

- エラーレベル: `Fatal error` / `Warning` / `Notice` / `Deprecated` の違い
- `php.ini` の `display_errors` / `error_reporting` / `log_errors` / `error_log`
- **本番でdisplay_errorsをOnにしてはいけない理由**（受託だと事故になる）
- `Error` と `Exception` の違い（PHP 7以降の `Throwable`）

### Day 3〜4: 例外処理

- `try / catch / finally`、`throw`
- 独自例外クラスを作る（`extends Exception`）
- 「握りつぶさない」catch の書き方（`catch (Exception $e) {}` で何もしないのが最悪）
- Laravelの `app/Exceptions/Handler.php` を読む

### Day 5〜7: ログ

- `storage/logs/laravel.log` を実際に `tail -f` しながらアプリを操作する
- `config/logging.php` を読む: **チャンネル**（single / daily / stack / stderr）の違い
- ログレベル: `emergency / alert / critical / error / warning / notice / info / debug` の使い分け
- `Log::info()` / `Log::error()` を自分のコードに仕込んで、変数の中身を出力する
- `.env` の `LOG_CHANNEL` / `LOG_LEVEL` を変えて挙動の違いを確認
- **例外に自分のコンテキストを乗せる**: `Log::error('決済失敗', ['user_id' => $user->id, 'exception' => $e]);`

**実践課題**: 自作アプリでわざと以下のエラーを起こし、**ログだけを見て**原因を特定する（画面は見ない）。

1. `.env` のDB接続情報を間違える
2. 存在しないメソッドを呼ぶ
3. 必須のリレーションが無いレコードにアクセスする（`Attempt to read property on null`）
4. バリデーションを通っていない値でinsertして、DBの制約違反を起こす

> ✅ 到達確認: `dd()` を使わずに、ログ出力だけでバグの発生箇所と原因の変数値を突き止められる

## Week 4: Xdebug とデバッグ実践

`dd()` デバッグから卒業する週です。

### Day 1〜2: Xdebugのセットアップ

Sail環境なら `.env` に `SAIL_XDEBUG_MODE=develop,debug` を設定 → VS Codeの PHP Debug 拡張 → `launch.json` の `pathMappings` を設定、という流れになります。

**ここは絶対にAIなしでやってください。** 一発で通ることはまずなく、
「ブレークポイントで止まらない → ポート9003は待ち受けているか → コンテナからホストへ到達できるか → パスマッピングは合っているか」
という切り分けそのものが、後半のインフラ学習の完璧な予行演習になります。

### Day 3〜5: デバッガーの操作

| 操作 | 意味 |
|---|---|
| ブレークポイント | ここで止める |
| ステップオーバー | 現在行を実行して次の行へ（関数の中には入らない） |
| ステップイン | 呼び出している関数の中に入る |
| ステップアウト | 現在の関数を抜けるまで実行 |
| ウォッチ式 | 任意の式の値を常時監視 |
| コールスタック | どこから呼ばれてここに来たか |
| 条件付きブレークポイント | `$id === 5` のときだけ止める（ループ処理で必須） |

**練習**: Laravelのリクエストが `public/index.php` からコントローラに届くまでを、ステップインで追いかける。ミドルウェアを通過する様子を目で見る。

### Day 6〜7: デバッグの"作法"

- **二分探索**: 怪しい範囲の真ん中にブレークポイントを置いて、前半か後半かを絞る
- **最小再現**: 余計なコードを削って、バグが再現する最小のコードを作る
- **仮説を口に出す**: 「$userがnullなはず」→ 確認 → 違った → 次の仮説。当てずっぽうでコードを変えない
- Laravel Telescope / `DB::listen()` で発行SQLを見る

> ✅ 到達確認: 未知のバグに対して「ログ → ブレークポイント → 変数確認」の順で30分以内に原因箇所を特定できる

# Phase 2: データベース（Week 5〜6）

## Week 5: SQL基礎

**Eloquentを一切使わず、生SQLだけ**で書く週にしてください。

- `SELECT` / `WHERE` / `ORDER BY` / `LIMIT`
- `INNER JOIN` / `LEFT JOIN` / `RIGHT JOIN` の違い（ベン図を自分で描けるように）
- `GROUP BY` と集計関数（`COUNT` / `SUM` / `AVG` / `MAX`）、`HAVING` と `WHERE` の違い
- サブクエリ、`IN` / `EXISTS`
- `INSERT` / `UPDATE` / `DELETE`、トランザクション（`BEGIN` / `COMMIT` / `ROLLBACK`）
- **インデックス**: 何が速くなるのか、なぜ全カラムに貼らないのか

**やり方**: 既存の自作アプリのDBにCLIで接続（`sail mysql` や `mysql -u root -p`）し、ターミナルから直接叩く。GUIツールは今週は封印。

**教材候補**: ミック『SQL 第2版 ゼロからはじめるデータベース操作』／SQLZOO などの演習サイト

## Week 6: テーブル設計とリレーション

- **正規化**: 第1〜第3正規形。何を防ぐための正規化なのかを説明できる
- **主キー / 外部キー / ユニーク制約 / NOT NULL**、外部キー制約の `ON DELETE` の挙動
- **リレーション**: 1対1 / 1対多 / 多対多（中間テーブル）
- **命名規則**: テーブル名は複数形、外部キーは `user_id`、中間テーブルは `role_user`（Laravel規約）
- **マイグレーション**: `up` / `down`、ロールバック、本番でのマイグレーションの怖さ
- **Eloquent**: `hasMany` / `belongsTo` / `belongsToMany` / `hasManyThrough`
- **N+1問題**: `with()` / `load()` によるEager Loading。`DB::listen()` で発行SQL本数を実際に数える

**実践課題**: 題材を1つ決めて（例: 勤怠管理、イベント予約、在庫管理）、ER図 → マイグレーション → シーダー → 一覧画面までを作る。
**必ず紙またはツールでER図を先に書いてから**手を動かすこと。受託では設計レビューが入るので、図で説明できることが重要です。

**教材候補**: 『達人に学ぶDB設計 徹底指南書』／『SQLアンチパターン』（後者は入社後でも可）

> ✅ 到達確認: 「多対多で中間テーブルに追加カラムが必要な場合どう設計するか」に答えられる

## Week 8: Nginx + PHP-FPM を手で構築する

**Sailを使わず、VM上に1から**Webサーバーを立てます。この週が「インフラで起こりうる問題を自己解決する」の土台です。

### Day 1〜3: 構築

1. `nginx` をインストール → `systemctl start nginx` → ブラウザで初期画面を確認
2. `php-fpm` をインストール → **Nginxは単体ではPHPを実行できない**ことを理解する
3. `/etc/nginx/sites-available/` にサーバー設定を書く
   - `listen` / `server_name` / `root` / `index` / `location` / `fastcgi_pass`
4. Nginx → PHP-FPM が **Unixソケット or TCPポート**で繋がっていることを設定ファイルで確認
5. Laravelアプリをデプロイして動かす（`root` が `public/` を向く理由を理解する）
6. MySQLもインストールしてアプリから接続

### Day 4〜5: 通信を理解する

- **ポート**: 80 / 443 / 3306 / 9000 が何のポートか
- `ss -tulpn`（旧 `netstat -tulpn`）: **どのプロセスがどのポートで待ち受けているか**
- `curl -v http://localhost` : リクエストとレスポンスのヘッダーを目で見る
- `curl -I` でヘッダーのみ取得、ステータスコードの確認
- HTTPの基本: メソッド、ステータスコード（200/301/302/400/401/403/404/419/500/502/504）、リクエストヘッダー / レスポンスヘッダー
- **502 Bad Gateway と 504 Gateway Timeout の違い** ← NginxとPHP-FPMの構成なら必ず遭遇します
- DNS: `dig` / `nslookup` / `/etc/hosts`
- `ping`（疎通）と `telnet host port` / `nc -zv host port`（**ポートが開いているかの確認**）
- ファイアウォール: `ufw status` / `ufw allow 80`

### Day 6〜7: ログの位置を体に入れる

| ログ | パス |
|---|---|
| Nginx アクセスログ | `/var/log/nginx/access.log` |
| Nginx エラーログ | `/var/log/nginx/error.log` |
| PHP-FPM | `/var/log/php8.x-fpm.log` |
| Laravel | `storage/logs/laravel.log` |
| MySQL | `/var/log/mysql/error.log` |
| システム全般 | `journalctl -xe` |

**重要な考え方**: エラーが出たとき、**リクエストの通り道の順にログを見る**。
`ブラウザ → (ポート/FW) → Nginx → PHP-FPM → Laravel → MySQL`
「どこまで届いているか」を確認すれば、原因の範囲は必ず絞れます。

> ✅ 到達確認: Nginx設定ファイルを見て、リクエストがどのファイルにルーティングされるか説明できる

## Week 9: 障害切り分け演習（**この週が集大成**）

Week 8で作った環境を**わざと壊して、自力で直す**週です。付箋やくじで壊す箇所をランダムに選び、記憶に頼れないよう1〜2日空けてから復旧するのがおすすめです。

### 故障シナリオ一覧

| # | 壊し方 | 学べること |
|---|---|---|
| 1 | Nginxを停止する | プロセス確認・`systemctl status` |
| 2 | Nginxの設定ファイルの `;` を消す | `nginx -t` による構文チェック |
| 3 | `listen` を8080に変える | ポートの理解、`ss -tulpn` |
| 4 | ufwで80番を塞ぐ | ファイアウォール、疎通と接続の違い |
| 5 | PHP-FPMを停止する | **502 Bad Gateway** の原因特定 |
| 6 | `fastcgi_pass` のソケットパスを間違える | Nginx error.log の読み方 |
| 7 | `storage/` の権限を `000` にする | パーミッション、実行ユーザー |
| 8 | `.env` のDB_HOSTを間違える | アプリ層とDB層の切り分け |
| 9 | MySQLを停止する | 接続拒否 vs タイムアウトの違い |
| 10 | PHPで無限ループを書き `max_execution_time` を超えさせる | **504 Gateway Timeout** |
| 11 | `root` を `public/` の1つ上に変える | Laravelのディレクトリ構成の意味 |
| 12 | ディスクを大きなファイルで埋める | `df -h`、ログ肥大化の怖さ |

### 復旧のたびに書き残すこと

```markdown
## 症状（ブラウザに何が出たか / ステータスコード）
## 立てた仮説（3つ）
## どのログ・コマンドで確認したか
## 実際の原因
## 次回、同じ症状を見たときに最初に打つコマンド
```

このドキュメントが**あなた専用の障害対応手順書**になります。入社後に一番効きます。

> ✅ 到達確認: 「アプリに繋がりません」とだけ言われた状態から、10分以内に原因のレイヤー（FW / Web / アプリ / DB）を特定できる

## Week 10: Docker基礎とDockerfile

### 概念

- コンテナと仮想マシンの違い（**なぜコンテナは軽いのか**）
- **イメージ**（設計図）と**コンテナ**（実体）の関係
- レイヤー構造とキャッシュ
- Docker Hub、公式イメージ、タグ（`php:8.3-fpm-alpine` の意味）

### コマンド

| コマンド | 用途 |
|---|---|
| `docker run` / `-d` / `-p` / `-v` / `--name` / `-e` | コンテナ起動 |
| `docker ps` / `docker ps -a` | 起動中 / 全コンテナ |
| `docker stop` / `start` / `rm` | 停止・再開・削除 |
| `docker images` / `docker rmi` | イメージ管理 |
| `docker logs -f <container>` | **コンテナのログ確認** |
| `docker exec -it <container> bash` | **コンテナの中に入る** |
| `docker build -t myapp .` | Dockerfileからビルド |
| `docker system df` / `prune` | 容量確認・掃除 |

`docker exec -it ... bash` で中に入り、Week 7で覚えた `ps aux` や `ss -tulpn` を打ってみてください。**「コンテナの中もLinuxだ」**という実感がつかめます。

### Dockerfile

- `FROM` / `WORKDIR` / `COPY` / `RUN` / `CMD` / `ENTRYPOINT` / `EXPOSE` / `ENV`
- `CMD` と `ENTRYPOINT` の違い
- `COPY` と `ADD` の違い
- レイヤーキャッシュを意識した順序（**`composer.json` を先にCOPYしてから `composer install`** する理由）
- `.dockerignore`

**実践課題**: 素のPHPイメージから、自分でDockerfileを書いて「Hello World」を返すPHPコンテナを起動する。

**教材候補**: Docker公式の Get Started／『仕組みと使い方がわかる Docker&Kubernetesのきほんのきほん』

## Week 11: Docker Compose で開発環境を自作する

**Sailを使わずに、Laravelの動く環境をゼロから組みます。** ここが上長の言う「入社後のトレーニングをDocker環境で行う」への直接の準備です。

### 構成

```
app (php-fpm)  ←→  web (nginx)  ←→  ホストの localhost:8080
      ↓
db (mysql)
```

### 学ぶこと

- `docker-compose.yml` の `services` / `build` / `image` / `ports` / `volumes` / `environment` / `depends_on`
- **ポートマッピング** `"8080:80"` の左右がどちらを指すか
- **ボリューム**: バインドマウント（ソースコード同期）と名前付きボリューム（DBデータ永続化）の使い分け
- **コンテナ間通信**: なぜ `.env` の `DB_HOST` が `127.0.0.1` ではなく **`db`（サービス名）** になるのか
  - → Composeが作る**ユーザー定義ネットワーク**内でサービス名がDNS解決される
  - `docker network ls` / `docker network inspect` で実際に確認する
- `docker compose up -d` / `down` / `down -v`（`-v` の破壊力に注意）/ `logs -f` / `exec`

### 通信の理解を確認する演習

1. `db` コンテナの `ports` を消す → **それでもアプリからDBに繋がる**ことを確認 → なぜか説明する
2. `web` コンテナに入って `curl http://app:9000` を叩いてみる
3. `app` コンテナから `ping db` して名前解決されることを確認
4. `DB_HOST` を `localhost` に変えて壊れることを確認 → **コンテナごとにlocalhostが違う**という感覚を掴む

**最終課題**: 自作Laravelアプリを、Sailを一切使わず自作の `docker-compose.yml` で動かす。`git clone` して `docker compose up -d` だけで動く状態にし、READMEに手順を書く。

> ✅ 到達確認: 「コンテナは起動しているのにブラウザで繋がらない」を、ポートマッピング / Nginx設定 / コンテナ間ネットワークのどこが原因か切り分けられる

# Phase 5: 総仕上げ（Week 12）

## Week 12: テストコード + 総合課題

テストは未経験とのことですが、**AIなしで開発するなら実はテストが一番の武器**です。手動で画面をポチポチ確認する時間が消え、壊れた瞬間が分かるようになります。

### Day 1〜4: PHPUnit / Pest

- **Unitテストと Featureテストの違い**（Laravelのディレクトリ構成そのまま）
- `assertEquals` / `assertTrue` / `assertNull` / `assertCount` などの基本アサーション
- HTTPテスト: `$this->get('/users')->assertStatus(200)->assertSee('田中')`
- `RefreshDatabase` トレイト、**テスト用DBの分離**（`.env.testing`）
- **ファクトリとシーダー**: `User::factory()->count(10)->create()`
- 認証が必要なページのテスト: `$this->actingAs($user)`
- モック（`Mail::fake()` / `Http::fake()`）の入り口だけ

**実践課題**: 自作アプリの主要機能に対してFeatureテストを10本書く。書いたあとにコードをわざと壊し、**テストが赤くなることを確認する**（赤くならないテストは意味がない）。

### Day 5〜7: 総合課題

小さくてよいので、**以下を全部満たすアプリ**を1本作ってください。

- [ ] 自作の `docker-compose.yml` + `Dockerfile` で環境が立ち上がる
- [ ] ER図をREADMEに載せる（多対多を1つ含む）
- [ ] マイグレーション + ファクトリ + シーダーが整備されている
- [ ] Featureテストが通る
- [ ] Xdebugが動く設定が入っている
- [ ] ログ出力を要所に仕込んである
- [ ] READMEに**セットアップ手順とトラブルシューティング**を書く
- [ ] **開発中、AIを一切使わない**（詰まった記録は学習ログに残す）

これがそのままポートフォリオ兼、入社初日の自己紹介材料になります。
